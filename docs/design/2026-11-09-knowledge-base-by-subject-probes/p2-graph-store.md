# P2 — Omnigraph 0.12.0 as OATS knowledge storage

## Question

Can a small, **local standalone** Omnigraph graph hold the current OATS knowledge corpus, answer the proposed subject/claim reading verbs, and replace Git's proposal, acceptance and citation workflow?

**Short answer:** yes to storage, typed traversal, full-text queries, isolated proposal branches, before/after entity changes, merge, and historical reads. **No, these do not amount to a drop-in replacement for the reviewed Git base.** Review authority, head-bound approval, publication screening, reader distribution and history retention need an application contract. JSONL export preserves data but **does not preserve commit citations on reload**.

Observed 2026-11-09 with the installed `omnigraph 0.12.0`. All engine calls used `--direct` and an explicit scratch store. No server, cluster, real knowledge-base write, push, PR, deployment change or external-material read occurred. `./work` was read-only for implementation inspection; its baseline test suite completed without source changes: **510 passed, 0 failed, 2 skipped** (512 total), exit 0, **123.64 s**.

## What I built

Everything is under `/tmp/kb-design/p2/`:

- `knowledge/`: local `git clone --no-hardlinks /tmp/kb-design/oats-knowledge knowledge`, exactly **1b6d6ea70f713176e7ce448ce849343a2bc6c986**. Its only remote points to that local clone, not GitHub.
- `loader.mjs`: dependency-free Node conversion, including a deliberately small scalar/flow-list frontmatter parser. It rejects unsupported metadata rather than silently dropping it.
- `schema.pg`: 2,761-byte OATS-only schema, generated by the loader. No external application schema was read or copied.
- `data.jsonl`: all 418 concepts plus subjects and relationships; `load-summary.json` and `about-audit.json` record counts and each About derivation.
- `queries.gq`, `benchmark.mjs`: reading queries and five fresh-process runs of each, both before and after `optimize`.
- `review-probe.mjs`: create proposal branch, load synthetic claims/verdict/edges, revise one body, inspect changes/history, merge, and compare historical reads.
- `portability-probe.mjs`: exact record comparisons, JSONL export/reload, historical-citation refusal, quiesced native-store copy.
- `run.mjs`, `measurements.jsonl`, `runs/*.stdout`, `runs/*.stderr`: exact argv, exit statuses and wall times. The harness strips inherited `OMNIGRAPH_*` variables and calls the installed binary by absolute path.
- `graph/`: original graph including the local review trial; `reload/`: fresh graph rebuilt from export; `native-copy/`: closed-process native copy. These are retained scratch evidence, not deployed stores.
- `export.jsonl`, `export.jsonl.gz`, `portability-summary.json`: portable data image and comparison result.
- `docs/`: public Omnigraph documentation pinned to **v0.12.0**, not current-version syntax.

### Mapping and the small schema

The supplied ontology sketch was followed:

| Original concepts | Graph type | Count |
|---|---|---:|
| Decision + Roadmap | Decision; kind decision/direction | 179 + 2 = 181 |
| Lesson + Conclusion + Limitation | Insight; kind lesson/finding/constraint | 213 + 13 + 5 = 231 |
| Reference | Reference | 5 |
| Playbook | Playbook | 1 |

Reference and Playbook remain separate document types; forcing all 418 records into Decision/Insight would contradict the sketch. Every concept keeps its original path as stable `slug`/identity, original `sourceType`, title, description, tags, timestamp, full body and source soul. Roadmaps get `status: proposed`; other imported status is explicitly `imported`, not an invented human-acceptance claim. The text/properties survived the round trip exactly.

Subjects: **8 System, 8 Workstream, 2 Project**. The first 14 primary subjects come directly from the node mapping; knowledge/messaging workstreams and both example projects complete the sketch's subject set. No project About relationship was invented for an existing concept.

About: **516 edges** = one primary per concept plus **98 distinct additional associations**. Secondary rules use an exact tag match against the six sketch words, or three or more body-link occurrences to existing concepts in another mapped node. Links resolve relative to the concept or base root; index/log links and external URLs are not counted. Repeated links count as occurrences, not distinct linked claims. This is a heuristic migration, not reviewed subject assignment.

The schema has three subject node types, four claim/document node types, Verdict, and 16 edge types. A generic `About: Claim -> Subject` using interfaces **failed** (details below), so it uses 12 concrete About types, plus SystemInWorkstream, ProjectInWorkstream, DependsOn and Supersedes. Each About edge is keyed by its endpoint pair. Bodies have `String @index`; timestamps have `Date`.

The source corpus has no structured `supersedes` metadata. Supersession is therefore tested with **three clearly synthetic decisions**, not inferred from arbitrary prose. Two illustrative membership edges connect `system/oats-okf` and `project/okf-5` to `workstream/knowledge`; they are marked as probe associations, not migrated accepted facts. The sole dependency, oats.okf → OATS kernel, is supported by this repository's README requirement `OATS >=0.69.2`.

Sizes are `du -sb`, `du -sB1`, and regular-file counts. They include graph history/index artifacts, not just live content. The optimized store remained small; this trial does not demonstrate a storage-capacity reason to leave Markdown.

The ordinary setup commands were:

```sh
cd /tmp/kb-design/p2
node loader.mjs
omnigraph --direct init --schema schema.pg ./graph
omnigraph --direct load --data data.jsonl --mode append ./graph --json
omnigraph --direct lint --schema schema.pg --query queries.gq --json
omnigraph --direct optimize ./graph
```

All 12 named queries linted with **zero errors/warnings**. Before any synthetic additions, export comparison verified **all 955 records and all property/endpoint values**, not merely counts.

After merging the fixtures, `probe/decision-v3 supersedes{1,8}` returned exactly **v2 and v1**, median **81.31 ms**, range **76.79–86.80 ms**. This proves bounded ancestor traversal, not an unbounded ordered-path API. The query sorts returned IDs; it does not project hop distance. A Verdict lookup by fixture hash returned `superseded` plus its reason in **69.53 ms**.

Representative GQ patterns, from the runnable file:

```text
query decisions_about_system($subject: String) {
  match {
    $s: System { slug: $subject }
    $c: Decision
    $c aboutDecisionSystem $s
  }
  return { $c.slug, $c.title, $c.description }
  order { $c.slug }
}
```

Other matches are `$s systemInWorkstream $w`, `$p projectInWorkstream $w`, `$s dependsOn{1,8} $d`, and `$new supersedes{1,8} $old`. Full-text uses `search($c.body, $term)` in `match`, with `bm25($c.body, $term)` projected and ordered descending.

**Polymorphism cost:** querying both System and Project members took two queries; searching all four claim/document types took four queries. The tested schema does not yield one generic About edge or a unified cross-type BM25 ranking. The sum of the four post-optimize search medians is about **158.50 ms**; independently scored per-type top tens are not a proven global top ten. A one-Claim-node/one-Subject-node design with kind properties is an alternative, but would change the prescribed three-subject/two-claim-type model and was not substituted silently.

### Proposal, review, merge, and citation

The standalone engine supports the workflow primitives; they are not server-only:

1. `branch create review/p2 --from main`: **25.02 ms**.
2. Load proposal on that branch: **50.75 ms**. Adds three fixture Decisions, three About edges, two Supersedes edges and one Verdict. `main` still has **181 Decisions**; proposal branch has **184**.
3. `commit changes <proposal-id>`: **59.41 ms**, nine inserts with type, ID, properties and edge endpoints.
4. A second branch load in merge mode changes only v3's body: **115.61 ms**. Its `commit changes`: **140.53 ms**, one update with complete **before and after properties**. This is real diff material, though not a rendered Markdown line diff.
5. `commit list`, `commit show`, and `query --snapshot <id>` worked. Reading v3 at the two branch commits returned its initial and revised bodies respectively.
6. `branch merge review/p2 --into main --as probe-reviewer`: **198.37 ms**, `outcome: fast_forward`, publishing a new commit with **both parent IDs** and the supplied actor. The source branch remains unless explicitly deleted.
7. `main` then has **184 Decisions**; the pre-proposal historical snapshot still has **181**. `commit changes <merge-id>` also exposes the net nine-entity accepted delta, including the revised body.

A result's `graph_commit_id` is returned **with the rows**. Example accepted snapshot from this trial:

```text
hb1.01M716HMZ0WANAM4Q7P4R3KS8G.3.01M716KV8VD966HYKXM5W0Z74F
```

Use the graph identity + claim ID + this **opaque** commit ID for a citation; it is not a Git SHA. `optimize` itself advanced graph history, so a commit change is not necessarily a knowledge-content change. Main's listed history follows its first-parent sequence and carries a separate `merged_parent_commit_id`; do not assume `commit list` is a flattened list of every proposal commit.

**What is still missing:** nothing in this no-policy store requires a maintainer to review or to be the merger. `--as` records attribution; it is not demonstrated identity authorization. Merging a fixture whose status is `proposed` leaves that property `proposed`. The app must define acceptance, validate verdict/claim transitions and keep consultation on the designated accepted branch. `branch merge --help` exposes no reviewed-source/target-head precondition flag; exact-head approval and concurrent-writer behavior therefore need qualification, not an analogy to GitHub's match-head merge gate. No concurrency or conflict scenario was tested.

### Export and another reader

- Initial corpus export: **111.23 ms**.
- Post-merge export: **103.98 ms**, **964 records**, **2,797,238 bytes**; gzip **839,470 bytes**. The separately supplied schema is 2,761 bytes.
- Initialize fresh local `reload/`: **32.99 ms**; load exported records: **166.51 ms**; export again: **172.85 ms**.
- Exact normalized comparisons proved all **964 exported entities, IDs, properties and endpoints** survived. The supersession query worked against the fresh store (**46.72 ms**).
- **But the source commit citation does not exist in the rebuilt graph.** It has new init/load commits and no original review branch/history.
- A quiesced native-directory copy took **12.41 ms**. A historical read with the original commit ID worked in the relocated copy (**43.06 ms**), and branch listing still showed `main` and `review/p2`.

Thus there is a shareable **data artifact** (schema + JSONL), and same-host evidence for a shareable **native store** retaining citations. **An actual second machine was not used.** Cross-platform compatibility, live coherent backups, incremental transfer, authenticated distribution and retention are unqualified. JSONL does not include a schema/history envelope; a reader installation needs those supplied separately. Public v0.12 documentation also warns that destructive cleanup can make historical reads unavailable, and that branch create/delete control should not run concurrently from separate writer processes.

### What would oats.okf have to change?

This is a **read-only source assessment**, not implemented or released graph support. Inspected worktree HEAD: **1d74816**. Its manifest says **5.8.0**, but it is ahead of released tag **v5.8.0 / ea5f6650e43e45808df066ae630398f42079ff92**. The listed core binding/consult/validation files have no diff against that tag; publication-helper/harvest/review guidance has later changes. No live released-provider graph integration is claimed.

These are provider concerns. The accepted kernel/capability boundary does not require adding a graph model or universal harvester to the kernel.

### Judgment for ~420 concepts

**What the agent gains:** typed relationship traversal, schema-checked references, a first-class multi-subject view without copying a claim, bounded dependency/supersession queries, ranked body search, atomic batches, and branch-local graph experiments with entity-aware change records. The query result can return exactly the titles/descriptions needed rather than a whole folder's Markdown. These are real capabilities in the tested binary.

**What it does not gain merely by changing storage:** correct subject assignment, accurate dependencies, meaningful supersession, promotion judgment, trustworthy acceptance, a better answer from an agent, or an owner for maintenance. Most relational benefits come from the **ontology**; the separate Markdown probe can test the same frontmatter semantics. The trial does not establish a performance crossover or superior retrieval quality.

**Cost:** a new query/data representation and polymorphism decision, multiple changed provider interfaces, a replacement for the GitHub review/event/lease machinery, native storage/index maintenance, distribution/backups and explicit citation retention. Rich prose still lives inside a string and benefits from text-oriented diff/rendering. The data volume is only a few MB and the observed performance is comfortably interactive, so scale is not a demonstrated forcing function.

**Recommendation for the parent design:** do not replace the authoritative Git base on this evidence alone. If richer traversal proves useful in the reading-verb comparison, an **optional derived graph index of an accepted Git commit** is the lower-governance-change experiment: retain original Git citations and reviewed acceptance while measuring a concrete graph retrieval benefit. That is a proposed next experiment, not adopted architecture. A graph-authoritative design first needs an explicit approved-review/distribution/retention contract and a second-machine rehearsal.

## Limits

- One installed Omnigraph **0.12.0** binary, one Linux host, standalone storage. No server/cluster, network graph, concurrent writers, conflict resolution, crash recovery, cleanup, live backup or cross-platform test.
- Five process-level timings per query; one load/init per store. OS caches were not flushed. Timing differences before/after optimization do not isolate an index speedup.
- Synthetic membership/supersession/verdict data demonstrates query mechanics, not facts extracted from 418 prose concepts. The dependency sample has only one verified edge.
- Finite traversal bounds are 1–8 hops. Global mixed-type ranked search, arbitrary-length chains and query-result quality were not established.
- Original source paths were kept as identity and prose links were not rewritten; the prototype is not a complete canonical-path migration.
- The sketch's verdict fields for PR links and complete acceptance provenance were not populated in the synthetic local fixture. No privacy/authority screen was implemented for the graph writes.
- Quiesced local copy is not a qualified second-machine or live-backup procedure. Export/reload is verified data portability only.
- Package tests are baseline verification, not evidence that oats.okf already supports this backend. The first `npm test` run was stopped by the harness's 120-second timeout before a suite summary. The longer-budget rerun completed: **512 tests, 510 passed, 0 failed, 2 skipped, exit 0, 123.64 s**. The two skipped real-OATS integration cases do not constitute live kernel verification.

## Approaches tried

1. **Installed CLI help + public version-pinned docs.** The guessed public docs path `operations/branching.md` returned HTTP 404; the correct v0.12 path is `branching/index.md`. A binary-string search was too noisy to use as syntax authority. Public docs plus actual CLI outcomes supplied the working syntax; no external schema or workspace was consulted.
2. **Interface-polymorphic About endpoints.** `interface-attempt.pg` declared Claim/Subject interfaces and concrete implementing nodes. Init failed in **34.49 ms**, exit **1**: `catalog error: edge 'About' has an unresolved endpoint`. Switched to concrete typed edge families, preserving the requested concrete node types.
3. **Whole-corpus JSONL append.** Succeeded in one load, all 418 concepts, no metadata parse failures or unmapped source types. Exact export comparison verified values. Reference/Playbook were retained rather than falsely converted.
4. **Queries before index maintenance, then optimize and rerun.** All worked in both passes. Recorded both timing series instead of attributing noisy differences to indexes.
5. **Explicit branch creation, append load, then merge-mode revision.** Isolation, commit history, historical reads and merge all worked standalone. Kept the review branch for retained evidence.
6. **Native `branch diff`.** Failed in **8.76 ms**, exit **2**: `error: unrecognized subcommand 'diff'`. Used `commit changes` instead; it supplied full before/after records, and historical reads independently confirmed the body revision.
7. **Schema + JSONL export/reload.** Data round trip passed. Reusing the source snapshot ID against the fresh graph failed in **39.15 ms**, exit **1**: `commit 'hb1.01M716HMZ0WANAM4Q7P4R3KS8G.3.01M716KV8VD966HYKXM5W0Z74F' not found`. No fallback silently relabelled the new commit as the old one.
8. **Closed-process native-store relocation.** Same-host copy preserved the original citation and both branch names. This is the narrower successful counterpart to JSONL's history loss, not an actual remote-reader rehearsal.
9. **Read-only oats.okf seam assessment and baseline suite.** No source edits. Binding/consult/validation findings were checked against HEAD and released v5.8.0; post-tag publication changes are explicitly distinguished above.
